```
'이 주장이 사실인가 팩트체크해줘'         → deep_analysis
'AI 반도체 시장에 대한 긴 보고서를 써줘'   → hyper_deep
'이 작업을 단계별로 수행해줘'             → recursive
```

### 1.2 판정 기준 (이 문서의 모든 판단이 여기서 나온다)

**품질/정확도 + 유지보수성/복잡도.** 비용과 지연시간은 판정 기준이 아니다.

§3.1의 결론을 좌우한다.

## 2. 차별점 — 무엇이 진짜 자산인가

### 2.1 검증된 클레임 기반 리포트 🥇

NEOS에서 유일하게 복제하기 어려운 자산이다. `DeterministicGrader`
(`neos/workflow/deep_analysis/graders/deterministic.py`)가 네 가지를 강제한다:

| 코드 | 강제하는 것 |
|---|---|
| `E_NO_EVIDENCE` | 클레임에 증거가 붙었는가 |
| `E_SOURCE_DEAD` | blob이 HTTP 2xx로 **실제 fetch**됐는가 |
| `E_QUOTE_MISMATCH` | 발췌가 **fetch된 원문에 문자 그대로 존재**하는가 |
| `E_CONFIDENCE_INFLATED` | 구별되는 출처 수로 confidence 상한 |

**핵심 성질은 grader가 출처 무관(source-agnostic)이라는 것이다.** 어떤 도구가 URL을
찾았는지 일절 보지 않는다. 이 비대칭이 전략적 뼈대다:

> **discovery는 자유롭게 넓히고, retrieval과 검증은 좁게 통제한다.**

Phase 1이 스킬을 discovery에만 넣고 retrieval을 `fetch.py` 독점으로 둔 것,
워커 LLM에게 도구 선택 자유를 준 것이 전부 이 원리에서 나왔다. 도구를 잘못 골라도
**미검증 주장이 통과할 수는 없다** — 주장이 적거나 나빠질 뿐이다.

### 2.2 append-only 이벤트 로그 + 결정론적 재생

- 이벤트 로그는 **DB 강제 불변식**이다 (D8). 관례가 아니라 제약.
- `cassette`가 `"search"`/`"fetch"`/`"llm"`/`"skill"` 네 종류를 녹화해 replay가 결정적이다.
- 이 두 가지가 **D19의 golden 회귀 게이트**를 떠받친다. 프롬프트를 바꾸면 매니페스트가
  깨져 재녹화와 신호 검토를 강제한다.

이건 단순한 로깅이 아니라 **개선 루프의 기반**이다. L5(`analytics.py`)가 이 로그를
read-only로 집계해 개선 신호를 만든다.

### 2.3 스킬 자동 발견

`discover_skills(skills_dir: Path)`가 임의 디렉터리를 스캔한다
(`neos/skills/manager/auto_discovery.py`, `SKILL.md` + `skill.py` 규약).
빌트인 15종 중 **연구 소스가 10종**이다.

Phase 1이 이걸 loop의 1급 discovery 소스로 승격시켰다 — 즉 **외부 스킬 = 외부 지식원**의
길이 열렸다. 다만 §3.3의 결함 때문에 아직 실현되지 않았다.

### 2.4 프레임워크 프리 코어

`deep_analysis`(3,464줄)는 **langgraph/langchain을 코드에서 전혀 import하지 않는다.**
내부 의존이 `settings`·`deep_analysis_models`·`web_search`·`time_utils` 넷뿐이다.
이것이 Phase 3(분리)의 비용을 낮게 유지한다.

## 3. 취약점 — 솔직하게

### 3.1 🔴 차별점이 기본값에서 꺼져 있다

deep 엔진 3종이 **전부 `enabled=False`**다 (`neos/config/schema.py`).
프로덕션 기본값에서 실제로 도는 것은 LangGraph workflow뿐이다.

즉 §2.1의 차별점은 **잠재적**이다. Phase 2가 R1을 닫아 "켜면 조용히 죽는" 문제는
사라졌지만, **켜는 결정 자체는 아직 안 내려졌다.** 남은 차단 요인은 §3.2다.

### 3.2 🔴 D18 선결 조건 #1 미해소 — wall-clock 무한

`_deep_analysis_orchestrator_node`가 `orch.run()`을 **타임아웃 없이** 동기 완주시킨다.

노드는 `profile="default"`를 하드코딩하므로 `global_token_cap` **300,000**,
`dig`의 `wall_clock_cap` 600s가 적용된다 (`service.py:88-92`가 `profile == "dev"`일 때만
dev 값 20,000을 씀). **D18 본문이 기록한 20,000은 dev 프로파일 값이며, 실제 노출은
기록의 15배다.**

챗 요청 하나가 수 분간 블로킹된다 → HTTP/WS/게이트웨이 타임아웃과 충돌.
**플래그를 켜기 전 반드시 해소해야 한다.** Phase 3이 구조적으로 없앤다(블로킹 노드 자체가 사라짐).

### 3.3 🔴 Phase 1의 학술 소스가 실질적으로 무력화돼 있다 — 신규 확인

Phase 1의 논거는 "arxiv·pubmed를 붙여 `source_tier`를 올린다"였다. **현재 그 이득이
실현되지 않는다.** 두 결함이 겹친다:

**(a) `fetch.py`가 HTML 전용이다.** `fetch_url`이 content-type 분기 없이 모든 2xx 응답에
`html_to_text(response.text)`를 적용한다 (`neos/workflow/deep_analysis/fetch.py:64-99`).
PDF를 넣으면 바이너리를 텍스트로 디코딩한 뒤 HTML 파서를 돌려 쓰레기 텍스트가 나온다.
status는 200이므로 `E_SOURCE_DEAD`를 **통과하고**, 대신 `E_QUOTE_MISMATCH`로 기각된다
— 즉 **원인이 오도된다.**

**(b) 내 정규화 로직이 PDF를 우선한다.** `skills_adapter.py`의

```python
_URL_KEYS = ("url", "link", "pdf_url", "html_url", "href")
```

arxiv 스킬은 `pdf_url`(PDF)과 `entry_url`(HTML 초록 페이지)을 **둘 다** 반환한다
(`neos/skills/builtin/arxiv/skill.py:120-121`). 그런데 `entry_url`이 키 목록에 **없어서**
`pdf_url`이 선택된다. **HTML로 정상 동작했을 URL을 두고 굳이 PDF를 고르는 구조다.**

결과: arxiv discovery는 검증된 클레임을 **0개** 산출한다.

> **이건 내가 만든 결함이다.** Phase 1 계획 단계에서 `fetch.py`의 content-type 처리를
> 확인하지 않았고, 스킬의 실제 반환 필드도 확인하지 않은 채 키 우선순위를 정했다.
> AC8("검증 사슬 무결성")은 통과했지만 — 사슬은 온전하고 클레임이 안 나올 뿐이다 —
> Phase 1의 **목적**은 달성되지 않았다.

**보정 방향 (구현 전 확정 필요):**
1. **최소 수정:** `_URL_KEYS`에 `entry_url`을 추가하고 **HTML URL을 PDF보다 우선**한다.
   비용 거의 0. arxiv가 즉시 동작한다.
2. **근본 수정:** `fetch.py`에 content-type 분기 + PDF 파서. 저장소에 이미 PyMuPDF 기반
   파서가 있다(`neos/workflow/pipelines/pdf_parser.py`, 470줄). 다만 이걸 끌어오면
   `deep_analysis`의 의존이 4개에서 늘어난다(§2.4와 상충).
3. **판단 보류:** 다른 스킬(pubmed·openalex 등)이 HTML URL을 주는지 실측한 뒤 결정.
   1번으로 충분하면 2번은 불필요하다.

### 3.4 🟡 검증 시스템이 이중화돼 있다

`deep_analysis/graders/`(결정론적+에이전틱)와 `workflow/harness/`(14파일, checkers 5종)가
**별개의 검증계**다. 전자는 loop 전용, 후자는 hyper_deep 전용.

유지보수성이 판정 기준이므로 이건 비용이다. 다만 **지금 통합할 근거가 없다** — 두
엔진의 역할이 Phase 2에서 막 분리됐으니(검증형 분석 vs 장문 리포트), 검증 요구도 다를 수
있다. **Phase 2 운영 데이터를 본 뒤 재검토한다.**

### 3.5 🟡 "있는 것처럼 보이지만 없는" 것 — 가장 위험한 범주

낡은 로드맵보다 위험하다. 낡은 항목은 "안 됐구나"로 끝나지만, 이건 **된 줄 알고 의존**한다.

| 항목 | 실제 |
|---|---|
| **다중 테넌시** | `Organization` 모델은 완비. **데이터 접근 경로 격리는 0.** 모델 존재를 격리 존재로 오인하기 쉽다 |
| **`autoResume`** | 이름은 재개인데 실제로는 **재실행**이었다 (FE 감사 발견). 이번에 재과금은 막았으나 **진짜 재개는 여전히 없다** — Phase 3 범위 |
| **`resume`** | `ledger.py:124`·`orchestrator.py:606` 주석이 "resumed run"을 전제하고 checkpoint 훅도 있으나 **진입점이 없다.** P4가 미완성 |

### 3.6 🔴 CI가 없다

`.github/`에 `dependabot.yml`뿐, **workflows 디렉터리 자체가 없다.**
프론트는 소스 202개에 테스트 9개(수정 후 31개)였다. 첨부가 405로 완전히 죽어 있었는데
아무도 몰랐던 이유가 이것이다.

백엔드도 취약하다 — `pytest tests/workflow/`는 basename 충돌로 **단일 실행이 수집 단계에서
실패**하고(`test_policy.py`·`test_executor.py` 중복 + `__init__.py` 부재), deep_analysis
테스트 37개는 Postgres 없이는 실패한다. **환경에 따라 통과 수가 달라지는데 이를 잡아주는
장치가 없다.**

이번 사이클에 고친 것들(재과금·강제 로그아웃)은 **리뷰로는 안 보이는 실패 모드**다.
조용한 되돌림 한 번에 회귀한다.

## 4. 전략 선택지

### 4.1 A — 검증형 분석에 집중 🥇 (권고)

**논지:** §2.1이 유일하게 복제하기 어려운 자산이다. 나머지(멀티모달·채널 봇·스케줄링)는
경쟁 우위가 아니라 **위생 요소**다.

| | |
|---|---|
| **함의** | §3.3 보정 → §3.2 해소 → Phase 3 완주. 차별점을 기본값에서 돌게 만든다 |
| **트레이드오프** | 오디오 STT·영상·협업·워크플로우 빌더가 뒤로 밀린다 |
| **왜 감수하나** | 차별점이 **꺼져 있고 심지어 무력화된 상태**(§3.1·§3.3)에서 영상 분석을 만드는 건 순서가 틀렸다 |
| **리스크** | Phase 3이 챗 계약을 바꾸는데 **FE 준비도가 "낮음"**이다(감사 §6). 플래그 격리 필수 |

### 4.2 B — 위생 요소 먼저

**부분 채택 권고.** 오디오 STT는 독립적이고 작다(의존 0). 곁가지로 붙일 만하다.
다만 **영상은 STT를 포함하는 더 큰 작업**이고, **협업은 Phase 3이 챗 계약을 바꾸므로
먼저 하면 두 번 만든다.**

### 4.3 C — 엔터프라이즈 축 (테넌시·감사)

이벤트 로그 패턴(§2.2)이 감사 로그로 바로 확장된다. 다만 **테넌시 강제는 모든 데이터 접근
경로를 스코핑**해야 하는 대규모·고위험 작업이다.

**타이밍:** Phase 3이 job 서비스를 세운 뒤가 자연스럽다 — job도 org 스코핑 대상이므로
먼저 하면 두 번 한다. **단, §3.5의 "격리가 있다는 착각"은 지금 기록해야 한다.**
구현은 나중이어도 오인은 지금 막는다.

### 4.4 D — 플러그인 생태계

로더는 이미 완성(§2.3)이고 Phase 1이 스킬을 discovery 소스로 만들었다. 실질 비용은
로더가 아니라 **샌드박싱·신뢰 모델**이다 — 외부 코드가 워커 안에서 돈다.

**권고:** §3.3 보정 이후. 그 전엔 "내부 전용 외부 디렉터리"로 한정.
마켓플레이스는 신뢰가 풀린 뒤의 문제다.

### 4.5 종합 권고

**A를 주축으로. 순서는 아래 §5.**

1. **A만이 차별점을 실재하게 만든다.** 지금 강점은 잠재적이고, 심지어 §3.3으로 무력화돼 있다
2. **C·D는 순서상 뒤다** — 둘 다 Phase 3 또는 §3.3에 의존한다. 먼저 하면 두 번 한다
3. **B의 나머지는 방향 충돌이거나 순서가 틀렸다** (§6)

## 6. 하지 않기로 한 것

핵심은 "안 좋아서"가 아니라 **"방향과 충돌해서"**다.

| 항목 | 이유 | 성격 |
|---|---|---|

| **영상 분석** | 오디오 STT도 미완인데 영상은 STT를 **포함**하는 더 큰 작업 | 순서 |

## 7. 이 문서가 정하지 않는 것

정직을 위해 명시한다.

- **§3.3의 보정 수준** — 최소 수정(1번)으로 충분한지는 **다른 스킬 실측 후** 판단.
  PDF 지원(2번)은 `deep_analysis`의 의존을 늘리므로 §2.4와 트레이드오프가 있다
- **§3.4 검증 이중화의 결론** — Phase 2 운영 데이터를 본 뒤 재검토. 지금은 근거 부족
- **플래그 활성화 시점** — §5의 1·2가 끝나야 판단 가능
- **CI 범위** — 어디까지 자동화할지(테스트만/린트/타입체크/e2e)는 별도 논의
- **미확인 항목** — 지식그래프 시각화(FE), 자동 스케일링, Ollama 온프레미스, 커스텀 웹훅.
  코드로 확인하지 못했으며 **미구현이라는 뜻이 아니다**

## 8. 요약

1. **차별점은 검증된 클레임이다**(§2.1). 핵심 성질은 **grader가 출처 무관**이라는 것 —
   discovery는 넓히고 retrieval·검증은 좁게 통제하는 **비대칭**이 전략적 뼈대다
2. **Phase 2가 R1·R2를 닫았다**(§1.1). 이제 세 엔진이 유형으로 갈리고, 켜도 조용히 죽지 않는다
3. **그러나 차별점은 여전히 꺼져 있고**(§3.1), **§3.2가 켜는 것을 막고 있다** —
   실제 노출이 D18 기록의 15배다
4. **Phase 1의 학술 소스는 무력화돼 있다**(§3.3). `fetch.py`가 HTML 전용이고,
   내 정규화 로직이 HTML URL을 두고 PDF를 우선한다. **내가 만든 결함이고, 보정이 1순위다**
5. **"있는 것처럼 보이지만 없는" 것이 낡은 로드맵보다 위험하다**(§3.5) —
   테넌시 격리 0, 진짜 resume 부재
6. **CI 부재가 이 모든 것의 회귀 위험을 떠받친다**(§3.6). 이번에 고친 것들은
   리뷰로 안 보이는 실패 모드다
7. **권고: §3.3 보정 → §3.2 해소 → 플래그 활성화 → CI → Phase 3.**
