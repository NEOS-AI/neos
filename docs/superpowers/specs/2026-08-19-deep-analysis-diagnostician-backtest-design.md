**작성일:** 2026-08-19
**트랙:** F — 개선 루프의 서브에이전트화 (`docs/DEEP_ANALYSIS_HARNESS_ROADMAP.md` §13)

신뢰할 수 없으면 루프의 4단계가 무의미하므로 §13.6이 이것을 선행으로 걸어뒀다.

## 1. 목적과 관문

§13.2가 나눈 네 역할(진단자·설계자·구현자·판정자) 중 **진단자**만 만들고, 그것이
쓸 만한지 **라이브 표본을 한 건도 쓰지 않고** 판정한다.

진단자의 계약(§13.2):

| | |
|---|---|
| 입력 | 표본 아티팩트 + 이벤트 원장만 |
| 출력 | 병목 후보 ≤3개, 각각 **근거 이벤트 id**와 함께 |
| 쓰기 | 없음 (읽기 전용) |

**관문:** 표본 #11~#16의 아티팩트만 주고 병목을 맞히는가. 정답은 이미
`DECISIONS.md` D53~D63에 있고, 이 백테스트는 그 기록된 정답으로 채점한다.

**이것이 트랙 F에서 가장 값싼 관문이다** — 정답이 이미 적혀 있고 라이브 표본을
소비하지 않는다. §9 **D-10**의 권고("읽기 전용부터")와도 맞는다.

## 2. 이 설계가 방어하는 것 — 오염

이 스펙을 쓰는 사람은 **정답을 이미 읽었다**(D53~D63). 그래서 두 경로로 백테스트를
무의미하게 만들 수 있다:

1. **진단자를 직접 연기한다** — 정답을 아는 사람이 진단하면 아무것도 재지 않는다.
2. **입력을 표본마다 고른다** — "이 표본에는 clamp 통계를 넣자"가 곧 정답 흘리기다.

설계가 둘 다 **구조로** 막는다:

- 진단자는 저장소 안의 **스크립트**다. 사람이 연기할 자리가 없다.
- 집계는 **표본을 모른다**. 같은 함수가 6개 표본에 그대로 돌고, 표본 id로 분기하지
  않는다는 것을 테스트가 단언한다.
- 정답키는 **채점기만** 로드한다. 진단 경로는 그 모듈을 import하지 않으며,
  렌더된 프롬프트에 정답키의 문자열이 없다는 것을 테스트가 기계적으로 확인한다.

## 3. 구성 요소

```
scripts/deep_analysis_diagnostician.py
  build_summary(rows, *, report_markdown, config_fingerprint)
                        집계 — 결정론. **표본 id를 받지 않는다**(§2)
  diagnose(input)       LLM 1회 호출 -> 라벨 ≤3 + 근거 event id + 이유
  score(pred, key)      recall@3 — 기계적

scripts/diagnostician_backtest/          <- 사전 등록, git에 있어야 한다
  labels.yaml           닫힌 라벨 집합 (17개)
  answer_key.yaml       표본별 truth / contemporaneous
  signal_map.yaml       라벨 -> 그 병목이 나타나야 할 요약 필드

artifacts/diagnostician-backtest/<UTC>/   실행 결과 (gitignore, 재생성 가능)
tests/workflow/deep_analysis/test_diagnostician_*.py
```

**`scripts/`에 두는 이유:** 표본 러너(`scripts/deep_analysis_funnel_sample.py`)와
같은 층이다. 진단자는 개선 루프의 도구이지 프로덕션 하네스가 아니다. F2~F4에서
실제로 재사용할 것이 보이면 그때 패키지로 옮긴다 — 지금 확장점을 먼저 짓는 것은
§13.5가 경계한 방향이다.

**순서:** 정답키·라벨집합·신호지도를 **먼저 커밋한다.** 사후에 정하면 판정이 아니라
합리화가 된다(§13.1).

## 4. 고정 스키마 집계

모든 표본에 **같은** 요약을 만든다. 원장의 어휘(이벤트 kind, stage)에서 기계적으로
유도하며, 사람이 표본별로 고르지 않는다.

- 이벤트 kind별 카운트
- stage별 예약/정산 (`token_budget_reserved` / `token_budget_settled`)
- clamp 통계 (`finalization_prompt_clamped`: `exhausted`, `dropped_primary`, 잔존)
- 게이트 결과 (`report_graded`: 코드 분포, `uncited_ratio`, `judge` 키)
- 정지 사유 (`token_budget_exhausted` / `..._at_floor` / `..._at_input_bound`)
- 강등 (`node_reduction_degraded`, `report_assembly_degraded`의 `reason`)
- 패스 결과 (`pass_completed`: status, tokens, verified)
- 배달물: `report.md` 본문, 각주 수, 원본 `[C:...]` 마커 수
- 구성 지문: `manifest.json`의 cap·floor·모델·임계값

**카세트는 넣지 않는다** (13MB). 넣어야 한다는 결론이 나오면 그것 자체가 발견이다.

> **요약이 신호를 빠뜨리면 그것은 실험의 결함이 아니라 계측의 결함이다.** §13.3이
> F1을 만든 이유가 정확히 이것이므로, 요약을 정답에 맞춰 늘리지 않는다.

## 5. 라벨 집합과 채점

**닫힌 집합 17개.** §3.1 파이프라인의 단계마다 라벨을 주고, #11~#16의 정답이
어디였는지와 **무관하게** 구성한다 — 라벨 집합이 정답 쪽으로 치우쳤는지는 "모든
단계에 라벨이 있는가"로 검사할 수 있다.

```
검색·증거   search_recall · source_quality · worker_extraction
채점        claim_grading · entailment_filter
조사        subquestion_coverage · investigation_budget · budget_floor_formula
리듀스      reduction_layer · degraded_join
조립        assembly_clamp · assembly_truncation · writer_prompt
리포트      citation_render · gate_definition · judge_budget
메타        instrumentation      <- "원인을 가를 수 없다"도 정답이 될 수 있다
```

**기준선을 둘 박아둔다** — 나중에 "50%면 좋은 건가"를 다투지 않기 위해서다.

| 기준선 | 값 | 뜻 |
|---|---|---|
| `random@3` | ≈ **17.6%** (3/17) | 아무 라벨이나 셋 고르기 |
| **`constant_best`** | **정답키에서 계산** | **아무것도 읽지 않는 최선의 고정 예측** |

🔴 **구속력 있는 기준선은 `constant_best`다.** 표본 #11·#13·#14·#15의 병목이 전부
`assembly_clamp` 계열이기 때문이다 — 그 넷은 *같은 병목을 해상도를 높여가며* 본
연속 표본이고, 그래서 연달아 돌린 것이다. 그 결과 `{assembly_clamp,
instrumentation, degraded_join}`을 **항상** 답하는 예측기가 6개 표본 평균
**66.7%**를 받는다.

이 값은 **스크립트가 정답키에서 직접 계산한다**(모든 3-라벨 조합을 훑어 최대
평균 recall을 구한다). 정답키가 바뀌면 기준선도 따라 움직이므로, 손으로 적어둔
수가 낡는 일이 없다.

> **라벨을 더 잘게 쪼개 넷을 갈라놓는 길도 있었지만 택하지 않았다.** 정답을 아는
> 사람이 라벨을 정답에 맞춰 재단하는 것이고, 그것이 §2가 막으려는 오염 그 자체다.
> **기준선을 밝히는 쪽이 정직하다.**

**채점식:** 표본별 `recall = |예측 ∩ 정답| / |정답|`. 정답이 둘 이상인 표본이
있을 수 있고, 몇 개가 그런지는 정답키를 쓸 때 확정된다(§10). 전체 점수는 6개
표본의 평균.

**근거 id 무결성 검사를 함께 건다.** 진단자가 댄 event id가 그 표본의 원장에
실제로 있는지 확인하고, 없으면 그 후보는 **폐기**한다 — §13.2의 "근거 없는 문장은
판정 대상이 아니라 폐기 대상"이다. 이 하네스에는 조립기가 존재하지 않는 클레임
id를 지어낸 전례가 있다(`E_ORPHAN_CITE`, D67). 같은 검사를 진단자에게도 건다.

**반복 3회.** 표본 6개는 얇아 4/6과 5/6이 잡음으로 갈린다. 표본당 3회 돌려 분산을
함께 기록한다(총 18회 호출). §10.2의 "표본 재실행 금지"는 **라이브 표본**에 대한
규칙이고, 이것은 기록된 아티팩트를 다시 읽는 것이라 해당하지 않는다.

**모델은 `powerful` 역할**(현재 `claude-opus-5`)로 고정하고 영수증에 모델 id를
남긴다 — 모델이 바뀌면 점수가 바뀐다.

## 6. 정답키 두 칸과 실패 해석

§13.3의 문장을 판정 가능하게 만드는 부분이다:

> "진단자가 같은 오답을 재현하면, 그 오답은 아티팩트만 봐서는 피할 수 없다는
> 뜻이고 부족한 것은 에이전트가 아니라 계측이다."

정답키에 칸을 둘 둔다:

| 칸 | 내용 |
|---|---|
| `truth` | 최종적으로 확립된 병목 (**나중 표본이 정정한 것 포함**) |
| `contemporaneous` | 그 시점에 사람이 실제로 내린 결론 |

§13.3이 지목한 대로 **#11과 #14**가 둘이 갈리는 표본이다 — #11은 존재하지 않는
기전을 쟀고(B-1·B-2), #14는 계측이 반쯤 틀렸다. **어느 표본에서 두 칸이 갈리는지는
정답키를 쓸 때 D53~D63을 직접 읽어 확정한다.**

결과는 세 갈래로 읽는다:

| 결과 | 뜻 |
|---|---|
| `truth` 적중 | 진단자가 작동한다. 정정된 표본이라면 **당시의 사람보다 낫다** |
| `contemporaneous`만 적중 | 사람의 오답을 재현했다 → **부족한 것은 계측** |
| 둘 다 빗나감 | 에이전트 문제인지 요약 문제인지 아직 모른다 → 아래 |

**셋째를 가르는 것이 신호 지도다.** 라벨마다 "이 병목이 있다면 고정 요약의 어느
필드에 나타나야 하는가"를 실행 **전에** 적어 커밋한다. 빗나간 라벨의 그 필드가
요약에서 비어 있거나 평평하면 입력에 애초에 없었던 것이고, 진단자 탓이 아니다.

**관문(통과 기준):** `truth` 기준 평균 recall@3이 **`constant_best`를 표본 한 건
이상 앞서는가** (≥ `constant_best` + 1/6). 초안 정답키에서는 66.7% + 16.7% =
**83.3% (5/6)**이다.

**왜 이 형태인가.** 원래 관문이던 "당시의 사람 4/6 ≈ 67%"는 `constant_best`와 같은
수여서, **아무것도 읽지 않는 예측기가 통과한다.** 그리고 5/6을 넘으려면
`assembly_clamp` 계열 밖인 **#12(`budget_floor_formula`) 또는 #16
(`subquestion_coverage`)** 중 하나를 반드시 맞혀야 한다 — 즉 이 관문은 총점이
아니라 **표본을 실제로 읽었는지**를 묻는다.

무작위(17.6%)를 넘는 것은 통과로 치지 않는다. `constant_best`만 겨우 맞추는 것도
통과가 아니다.

**F1이 실패해도 그것은 결과다.** 신호 지도가 "입력에 없었다"를 가리키면 다음 할
일은 진단자를 손보는 것이 아니라 **집계를 늘리는 것**이고, 라이브 표본을 쓰지
않으므로 곧바로 다시 돌려 확인할 수 있다.

⚠️ **눈금이 거칠다.** 표본 6개에서 한 건은 17%p다. 반복 3회는 표본 **내** 안정성만
주지 표본 수를 늘려주지 않는다. F1의 판정을 인과 주장처럼 인용하지 말 것.

## 7. 산출물과 영수증

```
artifacts/diagnostician-backtest/<UTC>/
  manifest.json              UTC·exit·git tree(clean?)·모델 id
                             ·라벨집합 해시·정답키 커밋 SHA·반복 수·사전 게이트
  inputs/<sample>.json       진단자가 실제로 본 것
  outputs/<sample>-<rep>.json  라벨 ≤3 · 근거 event id · 이유
  score.json                 표본별 recall · 세 갈래 분류 · 신호 지도 판정
```

**입력을 반드시 저장한다.** 진단자가 빗나갔을 때 "그 신호가 요약에 있었나"를 사람이
직접 확인해야 하는데, 입력을 남기지 않으면 그 질문에 영원히 답할 수 없다 — §10.1이
아티팩트 보존에서 배운 것과 같은 이유다.

**다만 이 아티팩트는 재생성 가능하므로** gitignore로 둔다. 재생성 불가한 것은
라이브 표본뿐이다. 대신 **정답키·라벨집합·신호지도는 git에 있다** — 그것이 사전
등록이고, 판정자는 사전 등록을 **커밋에서** 읽어야 한다(§13.2).

## 8. 테스트 전략

**LLM 호출은 테스트에서 완전히 배제한다.**

| 대상 | 어떻게 |
|---|---|
| `build_input` | 순수 함수. 픽스처 원장 행으로 스키마와 결정론을 고정. **표본 id로 분기하지 않는다**를 단언 |
| `score` | 순수 함수. recall 산식, 정답 2개짜리 표본, **없는 event id를 댄 후보는 폐기** |
| `diagnose` | 가짜 LLM 클라이언트. 닫힌 집합 밖 라벨 거부, 파싱 실패 처리 |
| **누출 금지** | 렌더된 프롬프트에 정답키 파일의 어떤 문자열도 없다는 것을 단언 |

누출 금지 테스트가 이 설계의 핵심 방어다 — 작성자가 정답을 안다는 사실이 프롬프트로
새는 경로를 코드가 막는다.

**실패는 삼키지 않는다.** 응답이 파싱되지 않거나 잘리면 재시도해서 점수를 만들지
않고, 그 반복을 **0점으로 기록하되 사유를 남긴다**(`unparseable` / `truncated` /
`off_label`) — `report_graded`의 `judge` 키가 굶은 판정자를 구분하는 것과 같은
어휘다. 파싱될 때까지 다시 묻는 것은 점수를 부풀린다.

## 9. 하지 않기로 한 것

- **쓰기 권한** — §9 D-10의 권고대로 읽기 전용부터. 구현자(F4)는 F1 결과를 보고 정한다.
- **라이브 표본** — 이 백테스트는 기록된 아티팩트만 읽는다.
- **요약을 정답에 맞춰 늘리기** — 그러면 재는 대상이 사라진다.
- **파싱될 때까지 재질의** — 점수 부풀리기.
- **설계자·판정자·오케스트레이션**(F2~F5) — F1의 답이 나오기 전에는 짓지 않는다.

## 10. 미결과 위험

| | |
|---|---|
| **라벨 입도** | 17개가 맞는 입도인지는 첫 실행이 말해준다. 너무 굵으면 전부 맞히고, 너무 잘면 정답 라벨이 갈려 recall이 낮게 나온다 |
| **정답이 둘인 표본** | 몇 개가 그런지는 정답키를 쓸 때 확정된다. 많아지면 recall 분모가 커져 점수가 보수적으로 나온다 |
| **당시의 사람 4/6** | §13.3의 서술에서 유도한 값이다. 정답키를 쓰면서 D53~D63으로 확인하고, 다르면 관문을 그 수로 고친다 |
| **라벨 겹침** | #11·#13·#14·#15의 정답이 `assembly_clamp` 계열로 겹친다. 표본 창(#11~#16)이 한 병목을 해상도를 높여가며 쫓던 구간이라 그렇다 — 라벨의 결함이 아니라 **표본 창의 성질**이다. `constant_best` 기준선이 이것을 드러낸다 |
| **표본 6개** | 얇다. §6의 경고 참조. `constant_best`를 한 건 앞선다는 관문도 결국 표본 한 건에 걸려 있다 |
