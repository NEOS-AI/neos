# 설계자 통과율 — 사전 등록

**작성일:** 2026-08-24
**대상:** `LlmGraphDesigner`가 실제 모델로 `validate_topology`를 통과하는 토폴로지를 내는가
**트랙:** G(§14.3 G2) / H(§15.3 H3) — H3를 켤 수 있는지의 관문
**규율:** §10.2(표본 1회) · §13.1(사전 등록이 표본보다 먼저)

> 🔴 **이 문서는 표본 실행 *전에* 커밋된다.** 실행 후 기대를 고치면 판정이 아니라
> 합리화가 된다(§13.1). 커밋 해시가 그 순서의 증거다.

---

## 1. 왜 재는가

`LlmGraphDesigner`의 호출자는 **테스트 12곳(전부 `_FakeModel`) + 프로덕션 1곳**이다.
검증된 것은 "모델이 이런 문자열을 주면 이렇게 파싱한다"까지이고, **실제 모델이 33개
노드 카탈로그를 받아 성립하는 토폴로지를 낼 수 있는지는 한 번도 관측된 적이 없다.**

§3.3의 표가 설계 §6.7·§6.8에 대해 적은 것과 같은 자리다 — "설계 의도이지 관측된
동작이 아니었다", `synth_pass` 0 / 574 run. 지금 `graph_design_enabled`를 켜면 매
요청이 LLM 설계를 태우고 전부 거부돼 정적으로 폴백할 수 있으며, **비용만 쓰고
아무것도 바꾸지 않는 상태**가 된다. 그리고 로그를 읽지 않는 한 조용하다.

## 2. 지표와 기대

| # | 항목 | 값 |
|---|---|---|
| **L-1 (1차)** | `validate_topology` 위반 0건인 설계의 비율 | **기대: < 30%** |
| **반증 조건** | 통과율 **≥ 50%** 이면 이 기대가 틀렸다 | |
| L-2 | 거부 사유 분포 — 어느 규칙이 몇 번 깨지는가 | 방향만 |
| L-3 | 파싱 실패율 (`InvalidDesignPayload`) | 방향만 |
| L-4 | 타임아웃율 (`graph_design_timeout_sec` = 20초) | 방향만 |
| L-5 | 승인된 설계의 노드 수 분포 | 방향만 |

**기대의 근거를 미리 적는다 — 사후 합리화를 막기 위해서다.**

- `response_generator.requires` = `{analysis_results, execution_start,
  generation_results, search_results}`이고 `GRAPH_ENTRY_WRITES`는 그중
  `execution_start` 하나만 준다. 나머지 셋을 쓰는 노드가 경로에 있어야 한다.
- 세 orchestrator가 전부 `required_agents`를 요구하고, 그것을 쓰는 노드는
  `query_classifier`와 `research_harness_repair` **둘뿐**이다.
- **내가 손으로 최소 통과 토폴로지를 찾는 데 세 번 걸렸다** — `response_generator`
  단독(위반 3) → 4노드 체인(위반 3) → 5노드 체인(위반 0). 카탈로그를 직접 읽고
  `validate_topology`를 반복 호출하면서다.

모델은 프롬프트 한 번만 보고 그 사슬을 맞춰야 한다. 낮을 것으로 본다.

## 3. 표본 설계

| 항목 | 값 |
|---|---|
| 크기 | 질의 **20개** × 설계 1회 = 20 호출 |
| 유형 | 대화형 5 · 검색형 5 · 분석형 5 · 복합 5 |
| 모델 | `graph_design_model = None` → everyday 역할 기본값 |
| 카탈로그 | `NODE_CONTRACTS` 전량 (실측 33개) |
| `mandatory` | `(response_generator,)` — 프로덕션과 동일 |
| `budget`/`node_costs` | **둘 다 `None`** — 프로덕션과 동일 |
| 실행 횟수 | **정확히 1회.** 실패해도 재실행하지 않는다 |

**알려진 편향 — 판정과 함께 반드시 인용할 것.** 질의 20개는 내가 만든다. 실제
사용자 질의 분포가 아니므로 **통과율의 절대값은 이 편향을 단다.** 유형 넷으로
균형을 잡았으나 그것이 대표성을 보장하지는 않는다. 이 표본이 답할 수 있는 것은
"모델이 이 과제를 원리적으로 할 수 있는가"이지 "프로덕션에서 몇 %가 통과하는가"가
아니다.

## 4. 판정 규칙

- **통과율 ≥ 50%** → 기대 반증. H3를 켜는 것이 현실적 선택지가 되고, 다음 관문은
  승인 재개(§8)와 gemini/ollama 배포다.
- **통과율 < 30%** → 기대 확인. **플래그를 켜지 않는다.** 다음 수는 배선이 아니라
  프롬프트·카탈로그 표현이며, 그것은 별도 사전 등록이다.
- **30~50%** → 판정 보류. L-2(거부 사유 분포)가 다음 수를 정한다 — 한 규칙에
  몰려 있으면 그 규칙이 다음 대상이고, 흩어져 있으면 과제 자체가 어렵다는 뜻이다.

**어느 경우에도 이 표본으로 프롬프트를 고치고 다시 재지 않는다.** 재려면 새 사전
등록이다(§13.5 "여러 변경을 한 표본에" 금지).

## 5. 산출물

`artifacts/graph-design-passrate/<UTC타임스탬프>/`

- `preregistration.md` — 이 문서의 사본 (커밋 해시 포함)
- `queries.json` — 질의 20개
- `responses/` — 원본 모델 응답 20개 (파싱 전)
- `verdicts.json` — 질의별 판정 (통과/거부+사유/파싱실패/타임아웃)
- `manifest.json` — 실행 영수증(PID, UTC start/end, exit status) + 구성 지문
  (모델 ID, 프로바이더, 카탈로그 크기, 타임아웃, 프롬프트 파일 해시)

§10.2가 요구하는 형식이다 — `20260725T081707Z`는 exit code를 복구할 수 없어
`unavailable`로 기록해야 했다.

## 6. 하지 않는 것

- 실패한 호출의 재시도 (§10.2 — 실패도 관측이다)
- 프롬프트·모델·타임아웃을 실행 중 변경
- 이 표본 하나로 인과 주장 — provider·시각 변동성을 판정에 명시한다
- 통과율을 프로덕션 예상치로 인용 (§3의 편향 때문에)
