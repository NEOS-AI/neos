**트랙:** G(§14.3 G2) / H(§15.3 H3) — H3를 켤 수 있는지의 관문
**규율:** §10.2(표본 1회) · §13.1(사전 등록이 표본보다 먼저)

> 🔴 **이 문서는 표본 실행 *전에* 커밋된다.** 실행 후 기대를 고치면 판정이 아니라
> 합리화가 된다(§13.1). 커밋 해시가 그 순서의 증거다.

## 1. 왜 재는가

`LlmGraphDesigner`의 호출자는 **테스트 12곳(전부 `_FakeModel`) + 프로덕션 1곳**이다.
검증된 것은 "모델이 이런 문자열을 주면 이렇게 파싱한다"까지이고, **실제 모델이 33개
노드 카탈로그를 받아 성립하는 토폴로지를 낼 수 있는지는 한 번도 관측된 적이 없다.**

§3.3의 표가 설계 §6.7·§6.8에 대해 적은 것과 같은 자리다 — "설계 의도이지 관측된
동작이 아니었다", `synth_pass` 0 / 574 run. 지금 `graph_design_enabled`를 켜면 매
요청이 LLM 설계를 태우고 전부 거부돼 정적으로 폴백할 수 있으며, **비용만 쓰고
아무것도 바꾸지 않는 상태**가 된다. 그리고 로그를 읽지 않는 한 조용하다.

## 2. 지표와 기대

| # | 항목 | 값 |
|---|---|---|
| **L-1 (1차)** | `validate_topology` 위반 0건인 설계의 비율 | **기대: < 30%** |
| **반증 조건** | 통과율 **≥ 50%** 이면 이 기대가 틀렸다 | |
| L-2 | 거부 사유 분포 — 어느 규칙이 몇 번 깨지는가 | 방향만 |
| L-3 | 파싱 실패율 (`InvalidDesignPayload`) | 방향만 |
| L-4 | 타임아웃율 (`graph_design_timeout_sec` = 20초) | 방향만 |
| L-5 | 승인된 설계의 노드 수 분포 | 방향만 |

**기대의 근거를 미리 적는다 — 사후 합리화를 막기 위해서다.**

- `response_generator.requires` = `{analysis_results, execution_start,
  generation_results, search_results}`이고 `GRAPH_ENTRY_WRITES`는 그중
  `execution_start` 하나만 준다. 나머지 셋을 쓰는 노드가 경로에 있어야 한다.
- 세 orchestrator가 전부 `required_agents`를 요구하고, 그것을 쓰는 노드는
  `query_classifier`와 `research_harness_repair` **둘뿐**이다.
- **내가 손으로 최소 통과 토폴로지를 찾는 데 세 번 걸렸다** — `response_generator`
  단독(위반 3) → 4노드 체인(위반 3) → 5노드 체인(위반 0). 카탈로그를 직접 읽고
  `validate_topology`를 반복 호출하면서다.

모델은 프롬프트 한 번만 보고 그 사슬을 맞춰야 한다. 낮을 것으로 본다.

## 3. 표본 설계

| 항목 | 값 |
|---|---|
| 크기 | 질의 **20개** × 설계 1회 = 20 호출 |
| 유형 | 대화형 5 · 검색형 5 · 분석형 5 · 복합 5 |
| 모델 | `graph_design_model = None` → everyday 역할 기본값 |
| 카탈로그 | `NODE_CONTRACTS` 전량 (실측 33개) |
| `mandatory` | `(response_generator,)` — 프로덕션과 동일 |
| `budget`/`node_costs` | **둘 다 `None`** — 프로덕션과 동일 |
| 실행 횟수 | **정확히 1회.** 실패해도 재실행하지 않는다 |

**알려진 편향 — 판정과 함께 반드시 인용할 것.** 질의 20개는 내가 만든다. 실제
사용자 질의 분포가 아니므로 **통과율의 절대값은 이 편향을 단다.** 유형 넷으로
균형을 잡았으나 그것이 대표성을 보장하지는 않는다. 이 표본이 답할 수 있는 것은
"모델이 이 과제를 원리적으로 할 수 있는가"이지 "프로덕션에서 몇 %가 통과하는가"가
아니다.

## 4. 판정 규칙

- **통과율 ≥ 50%** → 기대 반증. H3를 켜는 것이 현실적 선택지가 되고, 다음 관문은
  승인 재개(§8)와 gemini/ollama 배포다.
- **통과율 < 30%** → 기대 확인. **플래그를 켜지 않는다.** 다음 수는 배선이 아니라
  프롬프트·카탈로그 표현이며, 그것은 별도 사전 등록이다.
- **30~50%** → 판정 보류. L-2(거부 사유 분포)가 다음 수를 정한다 — 한 규칙에
  몰려 있으면 그 규칙이 다음 대상이고, 흩어져 있으면 과제 자체가 어렵다는 뜻이다.

**어느 경우에도 이 표본으로 프롬프트를 고치고 다시 재지 않는다.** 재려면 새 사전
등록이다(§13.5 "여러 변경을 한 표본에" 금지).

## 7. 판정 (2026-08-24, 표본 `20260824T101448Z`)

**아티팩트:** `artifacts/graph-design-passrate/20260824T101448Z/`
**영수증:** PID 58115 · UTC 2026-08-24T10:14:48 시작 · exit 0 · 사전 등록 `984ceced`
**구성:** `claude-sonnet-5` / anthropic · 카탈로그 31 · timeout 20s · budget hint 1000

### 7.1 L-1 — 기대가 반증됐다

**15/20 = 75%.** 기대는 <30%였고 반증 조건 ≥50%를 넘었다. **내 비관이 틀렸다.**

| 유형 | 통과 |
|---|---|
| conversational | **0/5** |
| search | 5/5 |
| analysis | 5/5 |
| composite | 5/5 |

부차 관측: 파싱 실패 **0** · 타임아웃 **0** · 에러 **0** (L-3·L-4). 승인 설계의 노드
수는 5개 11건 · 6개 3건 · 7개 1건 (L-5) — 내가 손으로 찾은 최소 통과 체인과 같은
크기다. **모델은 `requires` 사슬을 맞췄다.**

### 7.2 L-2 — 실패 다섯 건은 전부 같은 사유이고, 모델의 오답이 아니다

거부 사유는 **전부 `missing_mandatory`** 하나다. 모델이 설계한 것:

| # | 질의 | 설계 |
|---|---|---|
| 1 | 안녕하세요, 오늘 기분이 어때요? | `[direct_response]` |
| 2 | 당신은 무엇을 할 수 있나요? | `[refinement_checker, query_classifier, direct_response]` |
| 3 | 고마워요, 도움이 됐어요. | `[direct_response]` |
| 4 | 방금 한 말을 더 짧게 요약해 줄래요? | `[conversation_context_processor, direct_response]` |
| 5 | 당신의 이름은 무엇인가요? | `[direct_response]` |

**이것들은 옳은 그래프다.** "고마워요"에 검색·분석·생성 오케스트레이터를 지나갈
이유가 없다. 거부한 것은 `_DEFAULT_MANDATORY_NODES = (response_generator,)`라는
우리 규칙이고, **`direct_response` 도 응답을 만든다** — §14.2의 G1-a가 고친 것이
정확히 그것이다("`direct_response` 노드가 skip 경로에 답을 만든다", 사과문 제거).

즉 우리는 G1-a에서 `direct_response`를 응답 생산자로 인정해 놓고 `mandatory`
기본값에는 반영하지 않았다. §14.2가 남긴 문장이 이 결과를 미리 설명한다 —
"계약이 조건을 표현하지 못해 **진짜 버그와 무해한 경로가 같은 서명**을 낸다."
여기서는 그것이 **"옳은 설계와 빈 설계가 같은 거부를 받는다"**의 모양으로 왔다.

### 7.3 편향 재인용 (§3에서 미리 적은 것)

질의 20개는 내가 만들었다. **75%는 "모델이 이 과제를 원리적으로 할 수 있다"의
근거이지 프로덕션 통과율의 예측치가 아니다.** 유형별 결과가 0/5와 5/5로 갈린 것도
내가 유형을 넷으로 나눠 균형을 잡았기 때문이며, 실제 질의 분포에서 대화형 비중이
얼마인지는 이 표본이 답하지 않는다.

### 7.4 계측이 표본을 한 번 구했다

실행 전 dry-run에서 `catalog_size: 0`이 나왔다 — `NODE_CONTRACTS`는
`neos.workflow.graph`를 import해야 `@node_contract`가 채우는데 스크립트가 그것을
import하지 않았다. 그대로 돌렸다면 20회 전부 "빈 목록에서 노드를 고르라"는 불가능한
요청이었고, **통과율 0%를 "모델이 못 한다"로 오독**했을 것이다. §8.1.2의 "계측을
먼저 의심한다 — 루프는 틀린 지표에 성실하게 수렴한다"가 그대로 걸린 자리다.

### 7.5 이 표본이 바꾸는 것

| 차단 요인 | 상태 |
|---|---|
| ~~설계자가 실제로 작동하는가~~ | ✅ **해소** — 75%, 거부 사유 하나로 좁혀짐 |
| **`mandatory` 규칙이 대화형 질의를 전량 거부** | 🆕 **새 1순위** |
| 승인 재개가 정적 그래프에 묶여 있다 | 그대로 (§8, 스펙 `2026-08-23-graph-designer-wiring-g2-design.md`) |
| gemini/ollama 배포에서 설계자 생성 불가 | 그대로 |

**다음 수는 배선이 아니라 "응답을 만드는 노드"를 `mandatory`가 어떻게 표현할
것인가다.** 그리고 그것을 고친 뒤 다시 재려면 §13.5("여러 변경을 한 표본에" 금지)에
따라 **새 사전 등록**이다. 이 표본으로 고치고 다시 재지 않는다.
