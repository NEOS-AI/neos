## 🔴 P0 — 프로덕션 위험

### 1. 토큰을 쓰지 않는 워커 실패가 무한 루프를 만든다

**증상:** 워커가 매번 실패하되 토큰을 소비하지 않으면 오케스트레이터가 종료되지 않는다.

**근거 (실측):** `AlwaysFailingWorker`(`tokens_spent=0`)로 `Orchestrator.run()` 실행 →
**45초 경과까지 종료되지 않음.** 정지 밸브(D15)도 이를 막지 못한다.

**메커니즘:** 워커 예외 자체는 정상적으로 잡힌다 — `_run_worker`가 `status="failed"`와
`fail_reason`으로 변환한다(`test_exception_becomes_failed`가 고정). 문제는 그다음이다.
`Budgeter.should_stop()`의 정지 조건은 **소비 토큰과 score floor 기반**인데, 실패가
토큰을 쓰지 않으므로 예산이 줄지 않고 라운드가 무한 반복된다.

**현실적 트리거:** 워커 시그니처 불일치, API 키 만료·폐기, 검색/LLM 엔드포인트 장애 등
**계통적 실패**는 전부 이 형태다. 일시적 오류가 아니라 계속 실패하는 상황이 위험하다.

**영향이 실행자별로 다르다:**

| 실행자 | 바운드 | 결과 |
|---|---|---|
| Celery (`celery.enabled=true`) | soft 3600s / hard 3900s (Phase 3a) | 1시간 뒤 강제 종료 |
| **인라인 (현재 기본 구성)** | **없음** | `asyncio.create_task`가 **무기한 실행** |

`submit_deep_analysis_job`의 인라인 경로는 `asyncio.create_task(_execute(...))`를
타임아웃 없이 띄운다. 현재 `celery.enabled=False`이므로 **지금 구성이 바운드가 없는 쪽**이다.

> 참고: `9763eb5`가 추가했던 `node_wall_clock_cap`은 챗 노드에 걸린 것이었고,
> Phase 3b가 그 노드를 제거하면서 함께 사라졌다. job 경로에는 적용되지 않는다.

**제안:**
- 무진전 라운드 상한을 **토큰과 무관하게** 세는 종료 조건 추가 (D15 확장)
- 인라인 실행자에도 wall-clock 바운드 부여 (Celery의 soft limit과 동일 성격)

**해결 (2026-07-19):** 오케스트레이터에 토큰 소비와 독립적인 연속 계통 실패 상한을
추가하고, 인라인 실행 경로에 wall-clock timeout과 durable failure 기록을 추가했다.
항상 실패하며 토큰을 소비하지 않는 워커와 인라인 timeout 회귀 테스트로 두 종료 경계를
고정했다.

### 2. 기능 플래그를 환경변수로 켤 수 없다 — 조용히 무시된다

**증상:** `.env`에 `DEEP_ANALYSIS_ENABLED=true`를 써도 **아무 일도 일어나지 않는다.**
경고조차 없어 "켰다"고 착각하기 쉽다.

**근거:** `apply_legacy_env_overrides`(`neos/config/loader.py:275`)는
`LEGACY_ENV_KEYS`(`loader.py:129`) **허용목록에 있는 키만** 적용한다. 목록에 없는 변수는
경고 없이 버려진다. 확인 결과 아래 6개가 전부 목록에 없다:

```
DEEP_ANALYSIS_ENABLED   RECURSIVE_AGENT_ENABLED   HYPER_DEEP_AGENT_ENABLED
A2UI_ENABLED            RAY_ENABLED               EXECUTION_APPROVAL_ENABLED
```

`CELERY_ENABLED`도 마찬가지다 — `.env`에 `true`로 적혀 있으나 실제 값은 `False`다.

**해결 (2026-07-19):** 7개 YAML 전용 플래그를 명시적으로 등록했다. `.env` 또는
프로세스 환경에 이 키가 있으면 모든 실행 환경에서 `UserWarning`으로 무시 사실과 정확한
YAML 경로를 안내한다. 환경변수 값은 적용하지 않으므로 YAML이 계속 유일한 권위다.
일반 `*_ENABLED` 패턴은 외부 변수 오탐을 피하기 위해 경고하지 않는다.

## 🟡 P1 — 정확성·운영

### 4. 토큰 캡을 초과한다

**근거 (실측, `dev` 프로파일 cap 20,000):**

| 실행 | 소비 |
|---|---|
| 1회차 | 22,756 (+14%) |
| 2회차 | 27,362 (+37%) |
| 3회차 | 20,866 (+4%) |

**원인:** `should_stop`이 **라운드 경계에서만** 평가된다. 한 라운드 안의 병렬 패스가
캡을 넘겨 소비해도 그 라운드는 끝까지 간다.

**영향:** 예산이 상한이 아니라 **목표치**로 동작한다. 비용 예측이 빗나간다.

**해결 (2026-07-19):** 전체 심층분석 LLM 호출이 통과하는 중앙 어댑터에 run-scoped
하드 상한을 적용했다. 각 호출은 provider dispatch 전에 보수적인 입력 상한과 최대 출력량을
원자적으로 예약하며, 병렬 worker도 같은 `ContextVar` 예산을 공유하므로 합산 예약량이 캡을
넘지 않는다. 예약·정산·호출 전 해제 이벤트는 재사용 가능한 메모리 상태보다 먼저 ledger에
checkpoint된다.

재시작 시 이벤트를 순서대로 재생해 실제 정산량과 미종료 예약을 복원한다. provider 호출 후
예외·취소 또는 프로세스 중단으로 사용량이 불명확한 고아 예약은 전액 소비로 간주해
fail-closed한다. 상한 도달은 run당 한 번 기록·방출하며, worker partial 결과, 결정적 grader
판정, 계층 요약과 필수 섹션을 갖춘 결정적 보고서로 graceful degradation해 run을 완료한다.

### 5. Celery 브로커 장애 시 fallback이 없다

**근거:** `submit_deep_analysis_job`(`neos/tasks/deep_analysis_job_task.py:146`)은
`celery.enabled=true`이면 `apply_async`를 호출하고 **예외 처리가 없다.**

**영향:** 브로커가 내려가면 job 제출이 그대로 실패한다. 프로덕션에서 Redis 장애 =
심층분석 전면 중단.

**해결 (2026-07-19):** fail-loud 정책을 채택했다. `celery.enabled=true`인 환경에서
`apply_async`가 실패하면 인라인 실행자로 조용히 전환하지 않는다. 대신 새 DB 세션에서
run을 `failed`로 바꾸고 terminal `job_failed` 이벤트를 즉시 커밋한 뒤 제출자에게
`DeepAnalysisDispatchError`를 전달한다. 이벤트는 고정 코드 `E_BROKER_DISPATCH`와
비민감 고정 설명만 담아 broker URL·자격 증명·질문이 기록되지 않는다.

전용 start/resume API는 이 오류를 HTTP 503으로 변환한다. graph 경로는 기존 사용자 메시지
"심층 분석을 시작하지 못했습니다."를 유지하고 started 이벤트를 내보내지 않는다. 실패한
run은 explicit resume 대상에 남으므로 broker 복구 후 재개할 수 있다. Celery가 비활성화된
기본 구성의 bounded inline 경로는 변경하지 않았다.

### 6. `fetch.py`가 HTML 전용이다

**근거:** `fetch_url`(`neos/workflow/deep_analysis/fetch.py:64`)이 content-type 분기 없이
모든 2xx 응답에 `html_to_text(response.text)`를 적용한다.

**증상:** PDF를 넣으면 바이너리를 텍스트로 디코딩해 쓰레기가 나온다. HTTP 200이므로
`E_SOURCE_DEAD`를 **통과하고** `E_QUOTE_MISMATCH`로 기각된다 — **원인이 오도된다.**

**현재 우회:** `8dda86c`가 스킬 URL 우선순위를 HTML 랜딩 페이지 우선으로 바꿔 우회했다.
8개 빌트인 스킬은 전부 HTML URL을 제공하므로 당장은 문제가 없다.

**언제 다시 문제가 되나:** 외부 스킬을 받기 시작하면 URL 형태를 통제할 수 없다.
PDF만 제공하는 소스는 여전히 검증 불가다.

**트레이드오프:** `neos/workflow/pipelines/pdf_parser.py`(PyMuPDF, 470줄)가 이미 있으나,
끌어오면 `deep_analysis`의 의존이 4개에서 늘어나 **프레임워크 프리 성질**과 충돌한다.

**해결 (2026-07-19):** 기존 범용 parser를 결합하지 않고 deep-analysis 전용 text-only
PyMuPDF 어댑터를 추가했다. `Content-Type: application/pdf` 또는 공백 뒤 `%PDF-` magic
bytes로 PDF를 판별하고, 페이지 순서대로 추출한 텍스트를 HTML과 같은 공백 축약/NFC 규칙으로
정규화해 content hash 입력으로 사용한다. non-2xx와 기존 HTML 경로는 그대로 유지한다.

파서 import·open·page 오류는 안정적인 `PDFExtractionError`로 변환하며 내부 payload를
노출하지 않는다. worker는 이 예외만 URL 단위로 격리해 손상된 PDF 하나가 전체 조사를
중단하거나 HTML 쓰레기로 `E_QUOTE_MISMATCH`에 들어가지 않게 한다. 네트워크와 다른 코드
오류는 계속 상위로 전파한다.

구현 커밋은 `fea45b3`, `3967b91`이다. PDF 집중 회귀 25개와 변경 파일 Ruff가 통과했다.
함께 발견된 테스트 순서 문제는 `c891a24`에서 collection-time telemetry 전역 stub을 제거해
해결했다. sandbox에서 차단됐던 deep-analysis DB 테스트 46개는 구성된 로컬 PostgreSQL
접근 시 전부 통과했고, 최종 `tests/workflow tests/api/handlers` 전체는 **735 passed**였다.

### 7. verified 클레임 비율이 낮다

**근거 (실측, 검색어 버그 수정 후):**

| 실행 | 클레임 | verified |
|---|---|---|
| 2회차 | 14건 | **1건** |
| 3회차 | 10건 | **1건** |

**성격:** 크래시가 아니다. 시스템은 정직하게 동작한다 — 리포트가 확인된 것과 확인 못 한
것을 명시적으로 구분한다(설계 의도대로). 다만 **한 질의당 검증되는 사실이 1건**이면
심층분석의 실용성이 떨어진다.

**미확인:** 원인이 discovery 폭(소스 부족)인지, grader 임계값(`quote_match_threshold=0.92`)이
엄격해서인지, 워커 프롬프트 문제인지 구분하지 못했다. **분해 필요.**

**진단 계측 완료 (2026-07-19):** 판정 정책을 바꾸지 않고 verified claim funnel을
추가했다. deterministic grader는 evidence/source/fetched/dead 수, excerpt 문자 수,
기존 알고리즘의 최고 quote score와 적용 threshold를 `Verdict.diagnostics`로 전달한다.
orchestrator는 여기에 agentic tier의 `not_configured`, `skipped`, `attempted_passed`,
`attempted_rejected`, `exhausted` 상태를 병합한다.

ledger는 각 기존 claim outcome 이벤트 바로 전에 aggregate metadata만 담은
`claim_graded`를 기록한다. URL, excerpt, claim text, raw blob은 allowlist에서 제외했다.
analytics의 `claim_funnel`은 proposed/graded, deterministic·agentic 단계별 통과·실패,
verified/rejected/unverified, evidence 누락·dead source 비율, quote score bucket
(`exact`, `above_threshold`, `near_miss`, `low`, `unavailable`)과 evidence/source/excerpt
평균을 run 또는 기간 범위로 제공한다. malformed payload는 원시 totals에는 남지만 funnel
계산에서는 제외된다.

**남은 판단:** 이 구현은 병목을 관측 가능하게 만든 것이며 verified 비율 자체를 높인 것은
아니다. production-like 실행 표본에서 지배적인 손실 단계가 확인되기 전에는 threshold,
sampling, prompt, discovery 폭을 변경하지 않는다.

**프로덕션형 기준선 (2026-07-20):** 로컬 산출물 `20260720T142912Z`의 고정 질의 세트
`mixed-v1`로 `dev` 5회와 대표 질의의 `default` 1회를 측정했고, 6회 모두 완료됐다.
run ID는 `1569428d`, `edba7c4a`, `a98d0cc9`, `28aee7ae`, `9db9a983`,
`d6beaf77`이다.

- `dev` 합계: proposed 45, graded 49, deterministic rejected 27,
  agentic attempted/passed/rejected/skipped/exhausted 22/12/10/27/0,
  최종 verified/rejected/unverified 12/37/0이다. evidence missing과 source dead는 각각
  0%였고 quote bucket은 exact/above/near/low/unavailable 43/3/1/2/0이었다.
- 지배 손실은 최종 미해결 37건(graded의 75.5%)이다. `dev` reject code 37건 중
  confidence inflated 23건과 overclaim 9건이 32건(86.5%)을 차지했고, quote mismatch는
  4건, unsupported는 1건이었다. 따라서 evidence 발견 실패나 quote threshold 근처 손실보다
  클레임의 범위와 확신도 보정이 우선 병목이다.
- 동일한 `tech-free-threading` 질의에서 `dev`는 11,239 tokens로 graded 10,
  verified/rejected/unverified 2/8/0이었고, `default`는 222,667 tokens로 graded 251,
  79/136/36이었다. `default` 전체도 evidence missing 1/251, source dead 0으로
  discovery/source-dead 병목을 지지하지 않는다. 이 비교는 처리량 차이를 보여 주지만,
  profile별 단 1회이므로 효율이나 품질의 인과 효과를 뜻하지 않는다.

**다음 우선순위는 claim-generation/repair prompt 설계 하나로 한정한다.** 생성·수정 단계에서
근거가 직접 지지하는 범위로 클레임을 좁히고 확신도를 보정하는 방향을 먼저 실험한다.
threshold, discovery/source handling, agentic sampling은 이번 표본으로 변경하지 않는다.
이 결과는 단일 시점·고정 5질의·단일 Anthropic/Tavily 구성의 작은 표본이며 provider 변동,
시간 변화, 다른 질의 분포를 대표하지 않는다. 또한 지표는 distinct claim이 아닌 event 기반이라
재시도 때문에 proposed보다 graded가 클 수 있다. 이 기준선은 §7 비율 개선 완료를 의미하지 않는다.

**클레임 범위·확신도 보정 구현 (2026-07-21):** 위 `mixed-v1` 기준선에서 확인된 병목에
대해 생성 프롬프트와 파서 강제 장치를 함께 적용했다. worker prompt contract를 v2로 올려
클레임을 독립적으로 검증 가능한 단일 명제로 제한하고, 대상·시점·집단·조건·수치·비교 범위를
근거보다 넓히거나 상관관계를 인과로 바꾸지 않도록 명시했다. confidence 상한은 하드코딩하지
않고 실행 설정의 1개/2개/3개 이상 출처 상한을 prompt에 렌더링한다(`9c0ae8c2`).

worker는 fetch되지 않은 evidence를 제거한 뒤 고유 `source_url` 수를 계산해 confidence를
동일한 설정 상한으로 clamp한다. 0개 출처는 0.0이며, 중복 URL은 한 출처로 센다. 저장되는

default 질의 선택이 모두 표본 간에 달라졌으므로 위 변화를 entailment 도입의
**인과 효과로 확정하지 않는다.** 특히 default run은 질의 자체가 다르다. 또한
artifact에 model·threshold·cap의 구성 지문이 없어 실행 시점의 런타임 값 불변은
저장소 상태로만 뒷받침되며 사후 증명되지 않는다. 원 실행 세션(PID 86909)의
exit code와 wall start/end는 복구 불가로 `unavailable`이며, 완료된 내부 정합
artifact가 성공 증거다. 이 표본은 재실행하지 않는다.

**다음 구현 우선순위는 threshold·sampling·discovery·model·prompt·cap 변경이 아니라
entailment discard의 정당성(claim recall 손실) 측정이다.** 근거: 이번 표본의 가장 큰
변화는 verified 비율(+13.6%p)이 아니라 claim pool 축소(graded -42.1%, verified
절대수 -26.3%)이고, discard된 claim 중 evidence가 실제로 지지하던 비율을 모르면
비율 개선이 recall 희생의 산물인지 판별할 수 없다. keep/narrow/discard 결정을 claim
단위로 덤프해 discard 표본을 직접 검토하는 것을 먼저 수행한다. 잔존 overclaim
원인 분해는 그다음 순위로 둔다 — 근거는 점유율 변화(신호 아님)가 아니라 overclaim이
두 표본 모두에서 거부 코드의 대부분을 차지한다는 사실이다.

**후속 계측 과제(이번 평가에서 도출):** 향후 live 표본은 (1) PID·UTC
start/end·exit status·명령 동일성·test/Ruff/preflight 통과 boolean을 담은
secret-safe 실행 영수증과 (2) model ID·grader threshold·token/worker/depth/
wall-clock cap을 담은 구성 지문을 `manifest.json`에 함께 남긴다.

**해결 (2026-07-28):** discard-recall 측정 run의 **cassette 기록을 착수·완료했다**

않는다.

하나에만 귀속시킬 수 있다.

## ✅ 확인 및 수정 완료

### 15. `stream_manager`가 프로세스 내 메모리다

**결론:** `async_research`의 프로세스 간 스트리밍은 현재 깨져 있다.

- 제출 API는 소유권만 Redis에 기록하고 Celery `search` 큐에 작업을 보낸다. 이때
  `stream_manager` 세션은 만들지 않는다.
- SSE GET이 API 프로세스의 전역 `stream_manager`에 세션을 만든다.
- Celery 워커는 별도 프로세스의 전역 `stream_manager`에서 `workflow_started`,
  `workflow_completed`, `workflow_failed`를 발행한다.
- 워커 쪽에는 세션이 없으므로 `add_event()`가 `False`를 반환하며 첫 이벤트부터 폐기된다.
  API 쪽에 세션이 이미 있어도 프로세스 메모리를 공유하지 않으므로 결과는 같다.
- SSE 루프에는 유휴 종료가 없어 클라이언트가 끊지 않으면 heartbeat만 계속 보낼 수 있다.
  또한 현재 `Last-Event-ID` 요청 헤더를 읽지 않고 매번 전체 버퍼를 조회한다.

2026-07-19에 서로 다른 `StreamManager` 인스턴스를 API/워커로 둔 최소 재현에서 워커
`add_event()`는 `False`, API의 조회 이벤트 수는 `0`이었다. 기존 테스트는 단일 인스턴스의
소유권과 핸들러 mock만 검증하므로 이 프로세스 경계를 잡지 못한다.

**수정 완료 (2026-07-19):** 세션별 Redis Stream
`neos:async-research:events:{session_id}`를 추가했다. 워커는 `XADD`로 이벤트를 기록하고 API는
Redis entry ID를 SSE ID/커서로 사용해 `XREAD`한다. 최초 접속은 `0-0`, 재접속은
`Last-Event-ID` 이후부터 읽으므로 늦은 접속과 중복 없는 재연결을 지원한다.

- stream TTL 24시간, `MAXLEN ~ 1000`, read batch 100, block timeout 15초
- `workflow_completed`/`workflow_failed` 이후 종료, timeout 시 heartbeat
- Redis 읽기 실패는 terminal `stream_error`로 종료하며 무한 heartbeat로 숨기지 않음
- 워커의 시작/완료 발행 실패는 성공으로 위장하지 않고, 실패 이벤트 발행 오류는 원래
  워크플로우 재시도 원인을 보존함
- 구현 커밋: `700061e`, `3556f64`, `fc03954`
- 집중 회귀: 51 passed; 변경 파일 Ruff 통과
- 전체 workflow/API handler 실행: 663 passed, 62 failed. 실패는 sandbox가 차단한 PostgreSQL
  통합 테스트 44개와 선행 telemetry stub이 남는 기존 테스트 격리 문제 18개이며, 새
  스트리밍 집중 회귀에서는 재현되지 않음
